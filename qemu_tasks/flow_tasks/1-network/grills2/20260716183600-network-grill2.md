## Conclusions

The rewrite is structurally sound and stays inside the lane: one file
(`qemu/index.html`), plain JS, no framework, generated artifacts untouched. The
`start()` function is preserved byte-for-byte from the original, and the Phase-2
statement order (xterm -> openpty -> loadAddon -> `Module.pty` ->
`mainScriptUrlOrBlob` -> `info` -> `start(info)`) matches the original top-level
order, so the pre-existing pty/preRun sequencing is intact. Browser mode is
fully removed.

**No structural blockers.** All Grill-1 concerns were addressed. The remaining
items are risks and nits centered on brittle coupling to `arg-module.js`, silent
failure modes, and unverified boot behavior (the empty-input path in particular
is asserted-correct by code reading but has never been run — node is absent on
this host, per the Action notes). These should be named and handed to Test.

### Findings

**G2-1 [risk] — `disableGuestNetwork()` splice is brittle, positional coupling to `arg-module.js`.**
`index.html:229-234` finds `-netdev` via `indexOf` and does `args.splice(i, 4)`,
assuming the exact contiguous 4-tuple
`["-netdev", <val>, "-device", <val>]`. Today `arg-module.js:11` matches this
exactly and there is only one `-netdev` occurrence, so the current behavior is
correct. But this is hidden cross-file coupling: `index.html` now silently
encodes the *shape and ordering* of an array owned by a different module. If a
future edit to `arg-module.js` reorders args (e.g. `-device` before `-netdev`),
inserts an arg between the pair, adds a second `-netdev`, or splits the
`-device` onto the NIC differently, the splice will either remove the wrong 4
tokens (corrupting the QEMU command line and breaking *all* boots, networked or
not) or remove a partial/incorrect pair. There is no assertion that
`args[i+2] === "-device"` before splicing. Recommend at minimum a defensive
check (verify `args[i+2] === '-device'` and that `args[i+1]`/`args[i+3]` look
like the netdev/device values) and/or a comment in `arg-module.js` marking the
NIC tuple as load-bearing for `index.html`. Track as an accepted risk if left
as-is.

**G2-2 [risk] — Empty-input (air-gapped) boot is asserted, not observed.**
The Action resolves Grill-1 F1 by removing the NIC so SOCKFS never dials the
dead `ws://127.0.0.1:8888`. Code reading supports this: with no `-netdev`, the
guest has no virtio NIC, so no socket is created and
`websocket_sock_ops.createPeer` (out.js:3687+) is never reached. However the
Action explicitly notes node is not installed, so *no* boot was actually run —
neither the networked nor the air-gapped path. The claim "cannot hang" is a
structural inference, not a verified behavior. This is the exact risk Grill-1 F7
flagged. Hand to Test as a required observation: air-gapped boot must reach a
shell prompt without hanging, and the guest kernel must tolerate the missing NIC
(the `-append` line still carries `virtio_net.napi_tx=false`, which is harmless
without a NIC but should be confirmed not to stall init).

**G2-3 [risk] — Silent failure if `disableGuestNetwork()` finds no `-netdev`.**
If `indexOf('-netdev')` returns `-1` (arg-module.js changed, or load order
regressed so `Module['arguments']` is undefined), the function returns quietly
and the guest boots *with* the NIC on the empty-input path. That contradicts the
"empty = network disabled" acceptance criterion but produces no error, log, or
user-visible signal — the VM would silently attempt `ws://127.0.0.1:8888` again,
reintroducing the original F1 hang. A defensive `console.warn` when the expected
NIC tuple is absent would make this fail loud instead of silent. Nit-adjacent
but classed as risk because it can silently re-defeat the blocker fix.

**G2-4 [nit] — `Module['preRun']` array dependency is real but pre-existing and satisfied.**
Per the assignment's question: `out.js:406-410` `preRun()` does NOT create the
array — it only iterates `Module["preRun"]` if truthy. The array is initialized
solely by `load.js:175` (`(Module['preRun'] ??= []).push(runWithFS)`), which
runs at import time because `Module['calledRun']` is falsy on page load.
`index.html` loads `./load.js` via a classic `<script>` (line 163) before the
`<script type="module">` block, and classic scripts execute before module
scripts. So by the time `start()` runs `Module['preRun'].push(...)`
(index.html:237), the array exists. This is correct **but undocumented and
fragile**: `start()` assumes an initialized array with no guard (unlike load.js's
`??= []`). If the `load.js` tag were ever removed/reordered, `start()` would throw
`Cannot read properties of undefined`. No change required now; worth a one-line
comment noting load.js owns `preRun` initialization.

**G2-5 [nit] — Double-boot is guarded; a redundant Enter+click race is possible but harmless.**
The `booted` flag (index.html:183-189) is a synchronous top-of-function guard;
JS is single-threaded, so the second of any two events (Enter then click, or two
rapid clicks) hits `if (booted) return`. No double-boot. One residual: pressing
Enter in the input *and* the button firing are two distinct listeners, but they
cannot interleave mid-execution, so the guard fully covers it. Nit only: the
Enter handler does not `preventDefault()`; there is no `<form>` so no implicit
submit/navigation, but adding it would be defensive. Acceptable as-is.

**G2-6 [nit] — `normalizeUrl()` is minimal; several edge cases pass through unvalidated.**
Per the assignment's question: prepending `ws://` to a bare `host:port` yields
`ws://host:port`, which SOCKFS's regex `/ws[s]?:\/\/([^:]+):(\d+)/`
(out.js:3702) accepts. Good. But `normalizeUrl` only checks for a scheme; it does
not validate that a port is present or that the host is well-formed. Edge cases
that pass through and then fail *inside* SOCKFS (throwing
"WebSocket URL must be in the format ws(s)://address:port", surfaced only as a
guest socket errno, not to the user): (a) bare host with no port -> `ws://host`
fails the `:(\d+)` requirement; (b) trailing slash / path e.g.
`ws://host:8888/proxy` -> the regex still matches host+port (extra path is
tolerated by the `createPeer` object branch but the URL is passed verbatim to
`new WebSocket`, which is fine); (c) `wss://` is correctly preserved by the
scheme test. So the only genuinely broken input is "host without port", which is
accepted by the modal but dies silently later. Recommend either validate for a
`:port` and reject in the modal, or document malformed input as out of scope
(Grill-1 F2 already allowed the latter). Low value; nit.

**G2-7 [nit] — `n:` info-line omission on the no-network path is consistent, no confusion expected.**
Per the assignment's question: on empty input the `info` blob omits the
`n:<mac>` line (index.html:211-222). Since the NIC is also removed from the QEMU
args, the guest has no interface to assign that MAC to, so a missing `n:` line is
the correct/consistent state — there is no half-configured case where the guest
expects a MAC for a NIC that isn't there. The `info` file is consumed inside the
guest rootfs init (not in any JS here), so behavior can't be fully proven from
this repo, but the two signals (no NIC + no `n:` line) are congruent. No
structural issue; flagged only so Test confirms guest init does not block waiting
on a MAC/DHCP.

**G2-8 [nit] — Dead code / leftover references: index.html is clean; stale files remain on disk (expected).**
`index.html` has no remaining `Stack`, `stack-worker.js`, `c2w-net-proxy.wasm`,
`9999`, `192.168.127.253`, `getNetParam`, or `?net=` references (Grill-1 F3
confirmed `Stack`'s only consumer was the removed browser branch). The word
"browser" survives only in the page `<title>` (index.html:3, "container on
browser") — cosmetic, not a code reference; optionally retitle for the cyberpunk
theme. Note `qemu/stack-worker.js` and `qemu/dist/` still exist on disk but are
no longer referenced by `index.html`; leaving them is consistent with the brief
("do not regenerate/check in" does not require deletion). No dangling DOM: the
script references `#net-modal`, `#net-url`, `#net-connect`, `#net-offline`, and
`#terminal`, all of which exist in the markup.

**G2-9 [nit] — Cross-origin xterm imports over COEP.**
`index.html:165-166` imports xterm and xterm-pty from `https://unpkg.com` (module
imports). This is unchanged from the original and orthogonal to this task, but
under the server's `Cross-Origin-Embedder-Policy: require-corp`, cross-origin
subresources need CORP/CORS headers to load. These are ES module imports (subject
to CORS, which unpkg serves), not `require-corp` subresources, so they work today
— but it is a hidden external dependency (offline/unpkg-down => page fails to
boot). Pre-existing; noted for completeness, no action for this task.

  air-gapped boot and the `ping 1.1.1.1` networked path are both unverified.
