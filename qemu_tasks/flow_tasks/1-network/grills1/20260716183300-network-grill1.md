## Conclusions

The plan is scoped correctly (single file `qemu/index.html`, delegate path
preserved, generated artifacts untouched) and matches the brief and lane docs.
However there is **one blocker**: the plan's claim that empty input "disables
network" is not supported by the wiring. `arg-module.js` unconditionally adds a
QEMU `-netdev socket,connect=127.0.0.1:8888` NIC, and emscripten SOCKFS
(`out.js`) will still attempt a WebSocket connect even when `Module['websocket']`
is unset. The plan glosses over this and offers no test/observation to prove the
no-network boot does not hang. Several risks and nits below.

### Findings

**F1 [blocker] — "Empty input == network disabled" is unverified and likely false.**
`qemu/arg-module.js:11` always emits
`"-netdev","socket,id=vmnic,connect=127.0.0.1:8888","-device","virtio-net-pci,netdev=vmnic"`.
The plan forbids editing `arg-module.js` (correct per lane scope), so the guest
still gets a virtio NIC wired to a QEMU socket. In `out.js` SOCKFS
(`websocket_sock_ops.connect`, ~lines 3687-3760), when
`SOCKFS.websocketArgs["url"]` is empty it falls back to `url = "ws://"` and then
derives `ws://<addr>:<port>` from the socket target — i.e. it still tries to open
`ws://127.0.0.1:8888`. So omitting `Module['websocket']` does NOT prevent a
WebSocket connection attempt; it just points it at the default host:port with no
proxy listening. Result: on a no-network boot the guest NIC/DHCP will attempt to
connect to a dead `ws://127.0.0.1:8888`. Whether this hangs boot, spams errors,
or fails gracefully is unknown and untested. The plan must either (a) prove
empty-input boot reaches a shell promptly, or (b) explicitly record this as an
accepted risk with the observed behavior, or (c) escalate that true
"no network" may require an `arg-module.js`/scope change (out of current lane
constraint) — which would need a brief update. As written, acceptance criterion
"Empty input => network disabled" cannot be met by index.html changes alone.

**F2 [risk] — `ws://localhost:8888` (modal example) vs `connect=127.0.0.1:8888` (NIC).**
These are two different layers and the plan's "matches arg-module.js" comment is
misleading. The QEMU `-netdev socket connect=127.0.0.1:8888` is the *guest-side*
socket that SOCKFS intercepts; the `Module['websocket'].url` is the *actual*
WebSocket endpoint SOCKFS dials (it overrides the derived host:port). So the two
`8888`s are only coincidentally equal. A user is free to type any `ws://host:port`
in the modal and it will be honored regardless of the `127.0.0.1:8888` in
arg-module.js. Two consequences to name: (1) `localhost` vs `127.0.0.1` can
differ (IPv6 `::1` resolution, hosts file) — the example should ideally match the
proxy the test harness runs; (2) SOCKFS requires the format `ws(s)://host:port`
(it throws "WebSocket URL must be in the format ws(s)://address:port" on a bare
`host:port`). So `ws://` IS load-bearing — a user entering bare `localhost:8888`
will fail. The modal should validate/normalize the `ws://` prefix, or the plan
should state that malformed input is out of scope.

**F3 [nit] — Removing `<script src="./dist/stack.js"></script>` is safe.**
Confirmed: `Stack` is referenced only in `index.html:46` (browser mode, being
removed) and is defined by `dist/stack.js` (`Stack = __webpack_exports__`, built
via `webpack.config.js` name:'Stack'). No other consumer. `dist/stack-worker.js`
and `c2w-net-proxy.wasm.gzip` also become dead once browser mode is gone. Safe to
remove the tag. (Leaving the built files on disk is fine — brief says do not
regenerate/check in; it does not require deleting them.)

**F4 [risk] — Deferring xterm/pty creation to Phase 2 ("terminal after modal").**
The task says "2 phases": (1) modal, (2) load wasm+xterm. The plan reads this as
"create xterm + pty only after submit". That is a defensible literal reading, but
creating the terminal *first* (visible/greyed behind the modal) is the safer
reading and lower-risk: `Module.pty = slave` must be assigned before
`initEmscriptenModule(Module)` runs, and `openpty()`/xterm addon load ordering is
already known-good in the current file. Deferring xterm creation risks (a) a race
if any preRun/poll wiring assumes `Module.pty` exists at import time, (b) a blank
page while the modal is open with no terminal element. Neither reading is wrong,
but the plan states a firm decision without noting the ordering constraint that
`Module.pty` + the `onReadable`/poll preRun hooks must all be set before
`start(info)`/`initEmscriptenModule`. Recommend: build xterm+pty behind the modal
(Phase 1 renders both page and terminal container; Phase 2 = submit triggers
`start(info)` only). This keeps `start()` byte-for-byte and avoids reordering pty
setup.

**F5 [nit] — Enter-key submit and modal focus specified only loosely.**
Plan mentions "support Enter to submit" but not: autofocus the input, trap focus
in the modal, or prevent the page from being interactable before submit. Minor,
but list it as an explicit acceptance detail so the test agent can check it.

**F6 [nit] — COOP/COEP unaffected, confirm and stop worrying about it.**
`qemu/server.mjs` sets `Cross-Origin-Opener-Policy: same-origin` and
`Cross-Origin-Embedder-Policy: require-corp` (needed for SharedArrayBuffer). The
plan does not touch server.mjs, so isolation is preserved. One note: the modal is
same-origin inline HTML/JS — no new cross-origin subresource is added, so COEP is
not a concern for the modal itself. No action needed; recorded for completeness.

**F7 [nit] — Test expectation is under-specified for the empty-input case.**
Both the task and plan only test the *networked* path (`ping 1.1.1.1` with a live
proxy). There is no expected observation for the empty-input/no-network boot
(does it reach a shell? does `ping` fail cleanly?). Given F1, the empty-input
boot behavior is exactly the untested risk. Add an acceptance line: "empty input
=> VM boots to a shell prompt (network commands fail, boot does not hang)."

## Constraints/Dependencies

- Lane `qemu`: edits confined to `qemu/index.html`; `arg-module.js`,
  `server.mjs`, and generated artifacts (`load.js`, `out.js`, `*.wasm`,
  `*.data`, `dist/`) must not change. This constraint is what makes F1 a
  blocker rather than a quick fix.
- SOCKFS in `out.js` requires `ws(s)://host:port` URL format (F2).
- SharedArrayBuffer requires COOP/COEP from `server.mjs` (unchanged) — a live
  proxy on the entered `ws://` URL is required for the ping test; the page does
  not start it.
- Ordering: `Module.pty` and all `preRun` poll/onReadable hooks must be set
  before `initEmscriptenModule(Module)` (F4).
